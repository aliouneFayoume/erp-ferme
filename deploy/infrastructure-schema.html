Schéma d'infrastructure

ERP Massla — de la requête du navigateur à la sauvegarde chiffrée

Un seul serveur applicatif (VPS Oracle Cloud) derrière nginx, une base Postgres managée (Supabase) accédée avec un rôle restreint par RLS, et cinq services externes : PayDunya (encaissement Mobile Money), l'API WhatsApp de Meta (rappels), GitHub Actions (déploiement continu), Cloudflare R2 (sauvegardes) et OVH (DNS + certificat TLS). Les couleurs suivent le trajet d'une requête, pas la hiérarchie des boîtes.

Trajet applicatif — navigateur/WhatsApp → nginx → app → Postgres
Paiement — PayDunya, IPN, Wave/Orange Money
Messagerie — rappels WhatsApp via Meta
Déploiement — GitHub Actions (CI puis SSH)
Surveillance — health check + alerte ntfy.sh
Sauvegarde — pg_dump chiffré → Cloudflare R2, toutes les 6h

Un seul point de défaillance assumé

Un seul VPS (40.233.98.20) fait tourner nginx et l'app. S'il tombe, la sauvegarde chiffrée sur R2 permet de reconstruire ailleurs — c'est tout l'intérêt de l'externaliser.

Deux rôles Postgres, pas un

erp_app (RLS actif) sert l'application au quotidien ; erp_backup (BYPASSRLS, jamais utilisé par le code) sert uniquement à pg_dump — sans lui, la sauvegarde échouerait silencieusement sur les tables à policies.

La sauvegarde ne couvre pas que la base

server/.env et ovh.ini (clé de chiffrement, JWT, identifiants PayDunya/WhatsApp de chaque ferme) sont chiffrés en .gpg avant l'envoi vers R2 — perdre le VPS ne doit pas rendre ces secrets irrécupérables.

Double filet contre le silence

ntfy.sh alerte en cas d'échec détecté ; healthchecks.io est un "dead man's switch" qui alerte si la sauvegarde ne s'exécute pas du tout (VPS éteint, timer désactivé).
